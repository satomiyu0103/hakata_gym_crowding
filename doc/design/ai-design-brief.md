## この手順書の目的

「おしゃれにして」「いい感じにして」だけでは AI・デザイナーへの依頼がズレる。**何を定義すべきか**を媒体別に整理し、再現性のある `DESIGN.md` とプロンプトに落とす。

**学び始めの使い方**: 下の「用語・選択リスト」から各セクションで **1 つ以上選んで** Step 1 のブリーフに書くだけでよい。全部決めなくてよい。迷ったら「目的別クイック指定」から入る。

## 記事の要点（要約）

### 核心メッセージ

Web デザインには複数の観点がある。曖昧依頼は完成イメージのズレを招く。**14 の観点をテンプレート化して渡す**と、AI でも高い再現性で「おしゃれな画面」を作れる。

### 14 の観点（記事の骨格）

| # | 観点 | 決めること |
|---|---|---|
| 1 | 目的・ターゲット | 誰に・何を伝え・何をしてほしいか |
| 2 | 情報設計（IA） | 何を・どの順番で見せるか |
| 3 | ページ構成 | どのセクションでページを作るか |
| 4 | レイアウト | 要素をどう配置するか |
| 5 | ビジュアルスタイル | フラット、Bento UI、ミニマル等の流派 |
| 6 | トーン&マナー | ナチュラル、上品、信頼感等の全体印象 |
| 7 | カラー設計 | Primary / Accent / Background / Text 等の役割 |
| 8 | タイポグラフィー | フォント、サイズ、行間、階層 |
| 9 | コンポーネント設計 | ボタン、カード、フォーム等の部品 |
| 10 | UI 状態 | Default / Hover / Focus / Error 等 |
| 11 | 余白・角丸・影 | ゆとり、柔らかさ、立体感 |
| 12 | レスポンシブ | PC・タブレット・スマホの見え方 |
| 13 | アクセシビリティ | コントラスト、色だけに頼らない情報伝達 |
| 14 | デザインシステム | Design Token 化して再利用 |

### 記事が強調する依頼のコツ

- **避けたい印象**も一緒に伝える（甘すぎる、安っぽい、ごちゃごちゃ等）
- ビジュアルスタイルは **1 つに限定せず組み合わせ**（例: ミニマル × Bento UI）
- 色は「好きな色」ではなく **役割ごと**（Primary / Accent / Muted Text 等）
- 日本語は行間を広め（1.7〜1.8）、本文 16px 以上
- 最終的に **Design Token**（CSS 変数）として定義する

## 用語・選択リスト（ここから選ぶ）

各セクションで使う **よく使われる用語・パターン** のカタログ。初めは ★ のついた定番から選べば十分。

### 1. 目的・ターゲット

**目的（サイト・アプリでよく使う）**

| 目的 | デザインの方向性 | 選び方のヒント |
|---|---|---|
| ★ サービス登録を増やす | CTA を目立たせる | LP・オンボーディング向き |
| ★ 商品を購入してほしい | 写真・レビュー・価格を重視 | EC・予約向き |
| 企業の信頼感を伝えたい | 落ち着いた配色、整ったレイアウト | コーポレート・BtoB |
| 採用応募を増やしたい | 社員写真・カルチャー訴求 | 採用サイト |
| ブランドの世界観を伝えたい | 写真・余白・コピーのトーン | ブランドサイト |
| 機能・仕様を理解してほしい | 図解・ステップ・FAQ | SaaS・ドキュメント |
| 社内で合意を取りたい | データ・比較表・結論を明確に | パワポ・提案資料 |

**ターゲット（ペルソナの書き方例）**

- 20代後半の女性 / 30代前半のビジネスパーソン / 中小企業の経営者
- IT に詳しくない個人事業主 / 採用を検討している学生
- 子育て中の 30 代夫婦 / SaaS 導入を検討している法人担当者
- 高齢者（文字大きめ・操作シンプル） / 開発者（情報密度高め・ダーク UI 可）

**避けたい印象（そのままコピペ可）**

子どもっぽい / 甘すぎる / 派手すぎる / 安っぽい / ごちゃごちゃ / 押し売り感 / 古臭い / 堅すぎて近寄りがたい

### 2. 情報設計（IA）

**よく使う情報の流れ（LP・サービス紹介）** — この順番から選んで並べ替え

1. ★ ファーストビュー … 一番の価値を一言で
2. ★ 課題提起 … ユーザーの悩みに共感
3. ★ 解決策 … このサービスで何ができるか
4. ★ 特徴 … 強みを 3 つ程度
5. 利用ステップ … 3 ステップで説明
6. 実績・口コミ … 信頼感
7. 料金 … 判断材料
8. FAQ … 不安解消
9. ★ CTA … 登録・問い合わせ

**Web アプリで追加しがちなブロック**

ダッシュボード概要 / 一覧→詳細 / 設定・プロフィール / 通知センター / オンボーディング（初回チュートリアル）

**避ける構成（チェック用）**

最初から細かい機能説明 / 価値がわかる前に料金 / CTA がどこかわからない / 同じ情報の繰り返し

### 3. ページ構成（セクション名）

Web の **セクション名** はこの表から選ぶ。パワポは後述の「スライド構成」参照。

| セクション名（英） | 日本語の役割 | 入れる要素の例 |
|---|---|---|
| ★ Header | ヘッダー | ロゴ、グローバルナビ、ログイン |
| ★ Hero Section | ヒーロー | キャッチ、サブコピー、メインビジュアル、CTA |
| Problem Section | 課題 | 悩みの列挙、共感コピー |
| Solution Section | 解決策 | サービス概要、ビフォーアフター |
| ★ Feature Section | 特徴 | アイコン＋タイトル＋説明（カード） |
| Step Section | 手順 | 1→2→3 の利用フロー |
| Testimonial Section | 口コミ | ユーザー名、コメント、星評価 |
| Pricing Section | 料金 | プラン比較、おすすめバッジ |
| ★ FAQ Section | よくある質問 | アコーディオン |
| ★ CTA Section | 行動喚起 | 大きなボタン、補足文 |
| ★ Footer | フッター | 会社情報、リンク、SNS |

**Hero に入れがちな要素**: キャッチコピー / サブコピー / CTA ボタン / メインビジュアル / 実績数字（「利用者 10 万人」等）

**CTA 文言の例**: 無料ではじめる / 資料請求する / お問い合わせ / アプリをダウンロード / 相談予約する / 詳細を見る

### 4. レイアウト

**用語（プロンプトにそのまま使える）**

| 用語 | 意味 |
|---|---|
| カラム | 縦方向の列 |
| ★ 1カラム | 横幅いっぱいに縦積み（スマホ向き） |
| ★ 2カラム | 左右 2 列（左テキスト＋右画像 等） |
| 3カラム | 3 列でカード並べ |
| グリッド | 要素を規則的に並べる基準 |
| ★ 12カラムグリッド | Web でよく使う 12 列設計 |
| コンテナ幅 | コンテンツの最大横幅（例: 1200px） |
| セクション | ページ内の大きな区切り |
| ファーストビュー | 開いて最初に見える範囲 |
| カードレイアウト | 情報を箱に入れて並べる |
| ★ Bento UI | 大小さまざまなカードをグリッド状に（SaaS・AI 系で多用） |
| フルブリード | 画像や背景が端まで広がる |
| サイドバー | 左または右に固定ナビ |
| スティッキーヘッダー | スクロールしてもヘッダーが残る |

**代表的なレイアウト（用途から選ぶ）**

| レイアウト | 向いている用途 | 指定例 |
|---|---|---|
| ★ 1カラム縦積み | LP、ブログ、スマホ全般 | 「基本 1 カラム、セクション間は余白広め」 |
| 2カラム（テキスト＋画像） | 説明・比較 | 「PC のみ 2 カラム、スマホは 1 カラム」 |
| ★ カード 3 カラム | 機能紹介、料金、口コミ | 「PC 3 カラム、タブレット 2、スマホ 1」 |
| Bento グリッド | SaaS、AI、機能が多いサービス | 「重要機能は大カード、補足は小カード」 |
| ダッシュボード | 管理画面、分析 | 「左サイドバー＋上ヘッダー＋メインカード群」 |
| リスト＋詳細 | アプリのマスター画面 | 「一覧はリスト、タップで詳細へ」 |

**ブレークポイントの目安**

```
Mobile：〜767px ／ Tablet：768〜1023px ／ Desktop：1024px〜 ／ Large：1280px〜
```

### 11. 余白・角丸・影

**余白の用語**

| 用語 | 意味 | よく使う値 |
|---|---|---|
| Padding | 要素の内側余白 | カード 16〜24px |
| Margin | 要素の外側余白 | セクション間 48〜80px |
| Gap | グリッド・カード間 | 16〜24px |
| Section Spacing | セクション間 | PC 80px / SP 48px |

**角丸（border-radius）**

| 値 | 印象 | 向いているスタイル |
|---|---|---|
| 0px | シャープ・無骨 | ブルータル、エディトリアル |
| 4〜8px | 控えめ・ビジネス | コーポレート、フラット |
| ★ 12〜16px | 標準的・親しみ | 汎用、カード |
| 24px 以上 | やわらか・かわいい | Kawaii、ウェルネス |
| ピル型（9999px） | ボタン向け・親しみ | CTA、タグ |

**影（box-shadow）**

| 強さ | 印象 | 指定の言い方 |
|---|---|---|
| なし | フラット | 「影なし」 |
| ★ 薄い影 | 上品・軽い | 「whisper-soft shadow」 |
| 中程度 | カードの浮き | 「hover 時のみ影を追加」 |
| ベタ影 | ポップ | 「ネオブルータル風のベタ影」 |

### 12. レスポンシブ設計

**よく使う方針（そのまま指定可）**

- ★ モバイルファースト（スマホを先に設計）
- PC 最大幅 1200px 前後で中央寄せ
- ★ スマホは 1 カラム、PC は 2〜3 カラム
- ナビはスマホでハンバーガーメニュー
- ボタン高さ 44px 以上（指で押しやすい）
- 横スクロールを出さない

**画面別のレイアウト切り替え例**

| 要素 | Mobile | Desktop |
|---|---|---|
| 機能紹介 | 1 カラム縦積み | 3 カラムカード |
| Hero | 画像上・テキスト下 | 2 カラム（左文・右図） |
| フッター | 縦積みリンク | 横並び複数列 |

---

### 13. アクセシビリティ

**チェック項目（依頼文に入れる）**

- ★ 文字と背景のコントラストを十分に（本文 16px 以上）
- ★ エラーは色だけに頼らず文言も表示
- ボタン・リンクは 44×44px 以上
- 画像に代替テキスト（alt）
- キーボードだけでも操作可能（Focus 表示）
- `prefers-reduced-motion` でアニメーション控えめ

**改善例**: 「赤枠だけ」→「赤枠 ＋ 『メールアドレスの形式が正しくありません』」

### Web サイト / Web アプリ

記事の 14 観点をそのまま適用。Web アプリでは以下を追加。

### スマホアプリ

| 追加観点 | 内容 |
|---|---|
| プラットフォーム | iOS Human Interface / Material Design のどちらをベースにするか |
| 画面遷移 | タブバー / ボトムナビ / スタック / モーダル |

### パワポ（スライド）

| Web の観点 | パワポでの読み替え |
|---|---|
| 情報設計 | 1 スライド 1 メッセージ、ストーリーライン（起承転結） |

**スライド枚数の目安**: 本編 10〜15 枚、1 枚あたり箇条書き 3〜5 行まで。

### Step 2: 媒体別チェックリストで観点を選ぶ

- **共通**: 上記 14 観点
- **Web アプリ**: ナビ・データ密度・空状態を追加
- **スマホアプリ**: タッチ・遷移・プラットフォームを追加

### Step 3: `DESIGN.md` に落とす

プロジェクトルートの `DESIGN.md`（同梱雛形）に、Step 1〜2 の内容を埋める。

- 色は **描写名 + (#HEX) + 役割**
- 角丸・影は px だけでなく「やや丸み」「whisper-soft shadow」等の自然言語も併記
- 日本語 UI なら `awesome-design-md-jp` の例（SmartHR、note 等）を参照

### Step 4: AI に依頼する

Cursor チャットで次のように指定する。

```text

```

Stitch 連携時は `design-md` skill で既存プロジェクトから `DESIGN.md` を再生成も可。

### Step 5: レビュー（ズレチェック）

| チェック | 確認内容 |

| 一貫性 | ボタン・カード・色がページ/スライド間でブレていないか |

| レスポンシブ | スマホで横スクロール・押しにくいボタンがないか |

### 参考サイト収集フロー（playwright-cli）

ブラウザ自動化は **Playwright MCP ではなく CLI + skill** を使う（トークン効率・公式推奨）。

```text
1. playwright-cli open <url>
2. playwright-cli resize 1440 900  → screenshot --filename=refs/<site>-1440.png
3. playwright-cli resize 390 844   → screenshot --filename=refs/<site>-390.png
4. playwright-cli eval "JSON.stringify({...})"  → フォント・カラー・CSS変数
5. playwright-cli snapshot --boxes --filename=refs/<site>-ia.yml
6. 14 観点に沿って doc/design/design-refs/<site>.md に整理
```

- 出力先: `.playwright-cli/`（作業用・git 対象外）→ 整理後 `doc/design/design-refs/`
- デザインレビュー: `playwright-cli show --annotate`
- Windows で URL に `&` を含む場合: `playwright-cli --% goto "https://..."`
